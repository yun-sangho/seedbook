# 동기화 아키텍처 설계 (v2)

> 작성일 2026-11-28. 결정의 원본은 이 문서다 (조사 워크트리 `research-native-deploy` 에서 옮겨 보존).

> 작성: 2026-11-28, 워크트리 `research-native-deploy` (설계 문서, 커밋하지 않음)
>
> **이 문서의 역할**
> - 동기화를 운영의 핵심 시스템으로 두고, 스키마가 바뀌어도 데이터를 잃지 않는 **구조 자체**를 정한다.
> - 점검 결과와 손실 재현은 `sync-audit.md`, 배포·앱 구조는 `native-deploy.md` 에 있다. 이 문서는 그 위의 설계다.
>
> **사용자 결정 반영**
> - 충돌 단위 = **하위 항목 단위**.
> - 엔티티 정의 = **자체 소형 DSL**.
> - 모바일 웹은 접고 네이티브 앱만 남긴다.
> - 정식 사용자가 없다 → 옛 프로토콜(v1) 호환 없이 v2 로 바로 바꿀 수 있다.
> - **한 사용자가 여러 기기를 쓰는 일은 드물고, 동시에 편집하는 일은 더 드물다** → 동시 편집을 위한 장치는 두지 않는다 (§0.1).
> - **데이터에는 여러 버전이 있고 서버에는 최신 하나만 있다.** 저장 구조는 **서버 = 필드별 컬럼(RDB), 기기 = 레코드 JSON** (§2.5).
> - **서버 스키마는 확장만 한다 → 옛 앱도 동기화한다. 대신 확장 규칙을 CI 가 철저히 막는다.** 백업 불러오기는 파일 버전 ≤ 앱 버전일 때만. 데모 데이터 불러오기는 없앤다 (§7.1).
>
> **"권장 기본값"** 이라고 적은 것은 사용자 확인 전까지 이 값으로 설계를 진행한다는 뜻이다.

### 0.1 전제: 동시 편집은 거의 없다

이 설계의 무게는 **동시 편집이 아니라 시간 차이**에 둔다. 한 사람이 쓰는 앱에서 실제로 데이터를 잃는 경로는 다음 세 가지다.

- 옛 버전 앱이 새 필드를 모른 채 쓴다 (스키마 변화).
- 기기 저장이 깨진 값을 만나 지운다.
- 업데이트를 안 한 두 번째 기기, 재설치, 백업 복원, 모드 전환처럼 **오래된 사본**이 나중에 돌아온다.

그래서 남기는 것과 빼는 것은 이렇게 나뉜다.

| 장치                        | 판단                            | 이유                                                                                                                       |
| --------------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 패치 의미                   | **유지**                        | 동시성과 무관. 작은 전송, 필드 단위 거부, 오래된 사본이 안 고친 필드를 덮지 않음                                           |
| 모르는 필드 보존            | **유지 (기기 레코드 저장소에)** | 옛 앱도 동기화하므로 필요. 섀도가 아니라 기기 저장 레코드가 통째로 들고 있다 (§7.2)                                        |
| 하위 항목 단위 레코드       | **유지**                        | 충돌 때문이 아니라 ① 깨진 보유 종목 하나가 계좌 전체를 막지 않게(격리 단위), ② `delete-all+insert` 를 없앰                 |
| 삭제가 이김                 | **유지**                        | 규칙이 하나라 오히려 단순. 오래된 사본이 지운 걸 되살리지 않음                                                             |
| 격리 목록·재시도·426        | **유지**                        | 동시성과 무관                                                                                                              |
| `merge:"max"`·`mergeGroup`  | **제거**                        | 동시에 두 기기가 식물 단계를 바꾸는 경우를 위한 것. 남는 경우(모드 전환 병합)는 클라이언트 병합 함수 한 곳에서 처리 (§5.5) |
| 전역 시퀀스 + advisory lock | **사용자별 카운터로 단순화**    | 같은 효과를 사용자 행 한 줄 `UPDATE` 로 얻는다. Supavisor·drizzle 시퀀스 미확인 항목도 사라짐 (§4.4)                       |
| 두 기기 시뮬레이션 테스트   | **축소**                        | "오래된 기기가 돌아오는" 시나리오 하나로 (§9)                                                                              |
| 필드 단위 충돌 해결 로직    | **따로 만들지 않음**            | 패치 의미의 결과로 공짜로 생긴다. 같은 필드면 나중 도착이 이김, 그 이상 없음                                               |

## 1. 설계 원칙 (불변식)

이 여섯 가지는 코드·테스트·리뷰의 기준이다. 어기는 변경은 머지하지 않는다.

1. **무손실**: 사용자 데이터는 사용자의 삭제 동작으로만 사라진다. 검증·마이그레이션·버전 차이·모드 전환·재시도 어떤 경로로도 지워지거나 기본값으로 덮이지 않는다.
2. **패치 의미**: 쓰기는 "바꾼 필드"만 전달한다. 받는 쪽은 받은 필드만 바꾼다. 없는 필드는 "모름"이지 "비움"이 아니다. 비우기는 명시적인 값(`""`, `null`)으로 보낸다.
3. **확장만 하고, 모르는 것은 통과**: 스키마는 더하기만 한다 (§7.4). 어떤 계층도 모르는 필드·타입·enum 값 때문에 실패하거나 그것을 지우지 않는다. 높은 버전 데이터(앱보다 새 서버 응답 제외)는 받지 않는다.
4. **정의는 한 곳**: 레코드 모양은 DSL 정의 하나에만 적는다. 나머지는 모두 그 정의에서 만든다. 손으로 쓴 사본을 두지 않는다.
5. **모양 변경은 기계가 분류한다**: 정의가 바뀌면 `schemaVersion` 을 올리고, 깨는 변경이면 `MIN_SCHEMA` 와 `up` 단계까지 같은 PR 에. CI 호환 검사가 막는다 (§7.5).
6. **실패는 보인다**: 거부·격리·재시도 실패는 사용자 화면과 서버 로그 양쪽에 남는다.

## 2. 레코드 모델

### 2.1 레코드 타입

| 타입              | 부모          | 서버 테이블                   | 키                                 | 비고                                                                  |
| ----------------- | ------------- | ----------------------------- | ---------------------------------- | --------------------------------------------------------------------- |
| `account`         | —             | `investment_account`          | `id` (uuid)                        | `portfolioId` 가 연결의 원본                                          |
| `holding`         | `account`     | `stock_holding`               | `id`                               | 보유 종목                                                             |
| `cash`            | `account`     | `cash_item`                   | `id`                               | 현금 항목                                                             |
| `accountRecord`   | `account`     | `investment_record`           | `id` = **uuidv5(accountId, date)** | 날짜 키라 두 기기가 같은 날짜를 만들어도 같은 id 로 수렴              |
| `portfolio`       | —             | `portfolio`                   | `id`                               | `accountIds[]` 는 정리 대상 (§2.4)                                    |
| `allocation`      | `portfolio`   | `portfolio_allocation`        | `id`                               | 목표 비중                                                             |
| `rebalancing`     | —             | `rebalancing`                 | `id`                               | `result` 는 통째 값(json) 필드                                        |
| `rebalancingTask` | `rebalancing` | **`rebalancing_task` (신규)** | `id` (task.id)                     | 지금은 `tasks` jsonb. 매매 중에 가장 자주 바뀌는 것이라 레코드로 분리 |
| `settings`        | —             | `user_preference`             | `id` = userId (싱글턴)             | 마지막 envelope(설정)까지 레코드로 흡수                               |

- **파생 데이터는 동기화하지 않는다**: 계좌 일별 기록(`investment_account_snapshot`, 기기의 holdings history), 시세. 원본에서 다시 계산할 수 있고 기록 주체가 정해져 있다 (cloud = crawler, local = 기기). 지금처럼 별도 API 로 다룬다.

### 2.2 모든 레코드의 공통 열 (서버)

`id`, `userId`, `parentId` (하위 레코드의 부모 컬럼; 이름은 테이블마다 `accountId`·`portfolioId`·`rebalancingId`), `version`, `changeSeq`, `deletedAt`, `createdAt`, `updatedAt`, `sortKey`.

- 하위 테이블도 이 열을 갖는다. 지금은 루트에만 있다. **추가 마이그레이션 1회**가 필요하다.
- `updatedAt` 은 앱 시계 대신 DB `now()` 로 찍는다. 표시용이며 커서에는 쓰지 않는다.

### 2.3 충돌 규칙

- **필드 LWW**: 같은 레코드의 다른 필드를 두 기기가 고치면 둘 다 남는다. 같은 필드면 서버에 나중에 도착한 쪽이 이긴다.
  - 사람 한 명이 기기 사이를 오가며 쓰는 앱이라 "나중 도착 = 나중 의도"로 충분하다.
- **삭제가 이긴다**:
  - 톰스톤 레코드에 대한 패치는 `deleted` 로 거부한다. 클라이언트는 그 레코드를 지운다.
  - 실수 복구는 "되살리기"가 아니라 새 id 로 다시 만든다 (실행 취소 UI 는 클라이언트에서 보관한 값으로).
  - 부모를 지우면 서버가 같은 트랜잭션에서 하위 레코드에 톰스톤을 찍는다. 부모가 톰스톤이면 하위 레코드 생성·패치도 `parent_deleted` 로 거부한다.
- **병합 규칙은 두지 않는다** (§0.1): 서버는 모든 필드를 같은 규칙(나중 도착이 이김)으로 처리한다.
  - 식물 `growthStage` 가 내려가면 안 된다는 규칙(지금 `keepFurtherPlant`)은 모드 전환 병합에서만 의미가 있다. 그 병합은 클라이언트 함수 한 곳에서 `growthStage`·`goalAmount`·`goalHistory` 를 묶어 더 자란 쪽을 고른다 (§5.5).
- **불변식은 구조로 보장**: "한 계좌 = 한 포트폴리오"는 `account.portfolioId` 필드 하나로 표현하면 충돌이 생길 수 없다. 클라이언트·서버 정리 로직(`syncAccountPortfolioLinks`, `dedupePortfolioLinks`)이 필요 없어진다.

### 2.4 지금 구조에서 바꾸는 모양 (expand → contract)

| 변경                                                  | expand                                                                               | contract                                               |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| 하위 테이블에 공통 열 추가                            | 컬럼 추가 (nullable·default) + backfill                                              | —                                                      |
| `investment_record` id                                | `id` 컬럼 추가, backfill = uuidv5(accountId, date), 고유 인덱스                      | 기존 PK (accountId, date) 는 유지 (고유 제약으로 남김) |
| `rebalancing.tasks` → `rebalancing_task`              | 새 테이블 + backfill (jsonb 펼치기)                                                  | `tasks` 컬럼 제거                                      |
| `portfolio.accountIds[]` → `account.portfolioId` 원본 | 클라이언트·서버가 `portfolioId` 를 읽고 쓰게                                         | `accountIds` 제거                                      |
| `user_list_order` → `sortKey`                         | 레코드에 `sortKey` 추가 + backfill (현재 순서로 키 생성)                             | `user_list_order` 제거                                 |
| `changeSeq`                                           | `user_sync_state(userId, seq)` 테이블 + 컬럼 추가 + backfill (사용자별 updatedAt 순) | —                                                      |

- 정식 사용자가 없으므로 contract 를 같은 릴리스 주기 안에서 해도 된다. 그래도 순서(추가 → 코드 전환 → 제거)는 지킨다. 출시 뒤에 같은 절차를 그대로 쓰기 위한 연습이다.
- 마이그레이션 SQL 은 CLAUDE.md 규칙대로 `db:generate` 로만 만든다. 데이터 이동은 `db:backfill:*` 스크립트로 한다.

### 2.5 저장 구조: 서버는 컬럼, 기기는 레코드 JSON (사용자 결정)

**결정**: 서버는 지금처럼 **필드별 컬럼(RDB 스키마)** 을 유지한다. 데이터량이 작아 JSON 의 효율 문제는 크지 않지만, 스키마가 있는 테이블이 유지관리와 데이터 파악(Supabase SQL 로 바로 보기, 타입·제약을 DB 가 지킴)에 더 낫다.

이 결정이 확장 규칙(§7)과 맞물리는 이유:

- **서버는 모르는 필드를 담을 필요가 없다.** 서버는 늘 최신 스키마라 모든 필드가 컬럼으로 있다. `extra` 같은 JSON 칸을 두지 않는다.
- **모르는 필드를 보관해야 하는 곳은 기기뿐이다.** 옛 앱이 새 서버의 레코드를 받을 때만 생기는 문제다.
- 그래서 **기기 SQLite 는 레코드 JSON 테이블 하나**로 둔다.

|               | 서버 (Postgres)                                   | 기기 (SQLite)                                                                                                                                                                         |
| ------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 모양          | 레코드 타입별 테이블·컬럼 (지금 구조 + 공통 열)   | `records(type, id, parentId, data TEXT(JSON), checksum, schemaVersion, writtenBy, version, changeSeq, deletedAt, sortKey)` 하나 + `records_history` + outbox·섀도·격리. 무결성은 §5.7 |
| 모르는 필드   | 없음 (언제나 최신)                                | `data` 에 통째로 남음                                                                                                                                                                 |
| 필드 추가 때  | 정의 + `db:generate` (nullable/default 컬럼 추가) | **할 일 없음** (기기 마이그레이션 없음)                                                                                                                                               |
| 데이터 보기   | SQL 로 바로                                       | 기기 디버그 화면·백업 파일                                                                                                                                                            |
| 정의와 맞는지 | 대조 테스트 (정의 ↔ `schema.ts`)                  | 정의 검증(`parsePatch`)이 읽을 때 확인                                                                                                                                                |

- 기기는 서버와 달리 "사람이 들여다보는 원본"이 아니라 동기화 사본이자 local 모드 저장소라, JSON 의 약점(직접 조회·제약 없음)이 덜 아프다. 대신 지금 `lib/native/device-db/migrations.ts` 에서 서버 컬럼을 따라 손으로 하던 마이그레이션이 사라진다.
- local 모드 사용자의 데이터는 서버에 없으니, 기기 JSON 이 유일한 원본이다. 그래서 기기 쪽은 **저장 전 정의 검증 + 무삭제 + 격리**(§5.4)를 반드시 지킨다.
- 서버 컬럼 변경은 확장 규칙(§7.4)의 제약을 그대로 받는다: 추가는 nullable/default, 이름·타입 변경 금지, 제거는 깨는 변경 때만.

## 3. 레코드 정의 DSL (`packages/domain`)

### 3.1 모양

```ts
export const holding = defineRecord({
  type: "holding",
  table: "stock_holding",
  parent: { type: "account", column: "accountId", onParentDelete: "tombstone" },
  key: f.uuid(),
  fields: {
    market: f.text({ required: true }),
    ticker: f.text({ required: true }),
    name: f.text({ required: true }),
    currency: f.enum(CURRENCIES, { required: true }),
    quantity: f.decimal({ required: true, min: 0, normalize: "finiteOrZero" }),
    memo: f.text({ default: "", max: 1000 }),
    // 예: 나중에 추가되는 필드 — 정의에 넣고 schemaSteps 에 addField 단계를 적는다 (§7.2)
    // avgPrice: f.money({ default: null, nullable: true }),
  },
  sortable: true,
});
```

### 3.2 필드 종류 (10종 이내)

`text`, `enum`, `int`, `decimal`(유한 실수), `money`(원, 정수; 서버 bigint ↔ 클라이언트 number), `date`(YYYY-MM-DD), `timestamp`(ISO), `uuidRef`(다른 레코드 id; 없어도 허용), `bool`, `json`(통째 값 LWW — `result`, `goalHistory` 등).

### 3.3 필드 옵션

| 옵션                  | 뜻                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------ |
| `required`            | **생성** 때만 필수. 패치에서는 없어도 됨                                                   |
| `default`             | 생성 때 없으면 쓸 값. **패치에는 절대 적용하지 않는다** (원칙 2)                           |
| `normalize`           | 받은 값을 고쳐 쓰는 규칙 (`finiteOrZero`, `clamp`, `trim`). 고칠 수 있으면 거부하지 않는다 |
| `min`/`max`/`pattern` | 검증. 실패하면 **그 필드만** 거부                                                          |
| `serverOnly`          | `createdAt`·`updatedAt` 처럼 서버가 정하는 값. 클라이언트가 보내면 무시                    |
| `deprecated`          | 정리 예정. 읽기는 계속 지원, 새 코드에서 쓰기 금지 (린트)                                  |

### 3.4 정의에서 만드는 것

| 산출물                                                             | 사용처                                  | 대체하는 지금 코드                     |
| ------------------------------------------------------------------ | --------------------------------------- | -------------------------------------- |
| `parsePatch(raw, { op })` → `{ patch, rejected: [{field, code}] }` | 서버 mutation, 기기 저장, 백업 가져오기 | `parse*Fields`                         |
| `toColumns(patch, mode)` / `fromRow(row)`                          | 서버 repo                               | `*FieldsToColumns`, `*RowToData`       |
| `decompose(storeItem)` → 레코드들 / `compose(records)` → storeItem | 클라이언트 동기화 계층                  | `*-sync-config.ts` `toData`/`fromData` |
| `diff(base, next)` → 패치                                          | 클라이언트 outbox                       | `recordLocalChange` 의 비교            |
| 기기 레코드 읽기·쓰기 (`records` 테이블 하나, 검증 포함)           | `device-db`                             | `table-envelopes.ts` 손 SQL            |
| 백업 형식 `export`/`import`                                        | 설정 화면 백업                          | 번역기·백업 코드                       |
| 테스트 생성기 (임의 레코드, 버전별 옛 payload)                     | 테스트                                  | 없음                                   |
| drizzle 스키마와 일치 검사                                         | 테스트                                  | 일부 (`migrations.test.ts`)            |

- **drizzle 스키마는 생성하지 않고 대조한다.** DB 스키마는 마이그레이션 생성 규칙 때문에 `schema.ts` 에 손으로 두되, 정의와 컬럼·타입·nullable 이 같은지 테스트로 막는다.
- **기기 SQLite 는 레코드 JSON 테이블 하나라 필드 변경에 마이그레이션이 없다** (§2.5). 기기 마이그레이션은 `records`·outbox 같은 저장 틀이 바뀔 때만.

## 4. 전송 프로토콜 v2

### 4.1 공통

- 헤더:
  - `x-seedbook-sync: 2` — 프로토콜 정수.
  - `x-seedbook-schema: N` — 앱의 데이터 버전 (§7).
  - `x-seedbook-client: <앱 번들 버전>` — 로그용.
  - `Authorization: Bearer …` — 번들 앱 기준. `native-deploy.md` §A1.
- 서버는 데이터 버전 `[MIN_SCHEMA, CURRENT]` 를 받는다. 낮으면 `426 { minSchema }`, 높으면 `409 { code: "schema_ahead" }`.
- 앱은 시작·복귀 때 `GET /api/sync/version` 으로 먼저 확인하고, 구간 밖이면 push/pull 을 시작하지 않는다.
- 서버는 버전별로 다르게 동작하지 않는다 (변환 없음). 버전은 게이트와 로그에만 쓴다.

### 4.2 쓰기 `POST /api/sync/push`

```json
{ "ops": [
  { "type": "account", "id": "…", "op": "create", "fields": { … }, "sortKey": "a0" },
  { "type": "holding", "id": "…", "parentId": "…", "op": "patch", "fields": { "quantity": 12 } },
  { "type": "cash", "id": "…", "op": "delete" }
] }
```

- `op`:
  - `create`: 필수 필드가 다 있어야 한다. 이미 있으면 patch 로 처리한다 (재전송 멱등).
  - `patch`: 없는 레코드면 `not_found` 를 돌려준다. 클라이언트는 섀도가 없으니 `create` 로 다시 보낸다.
  - `delete`: 멱등.
- **사용자별 직렬화**: 요청 하나를 한 트랜잭션으로 처리하고, 맨 앞에서 사용자 카운터 행을 올린다 (§4.4). 그 행 잠금 때문에 한 사용자의 쓰기는 하나씩만 커밋된다 → `changeSeq` 순서 = 커밋 순서. 동시 요청이 드무니 기다림도 거의 없다.
- ops 는 순서대로 적용한다. 부모 `create` 가 같은 요청 앞쪽에 있으면 하위 `create` 가 성공한다. 클라이언트는 부모를 먼저 넣어 보낸다.
- 결과 (ops 와 같은 순서):

  ```json
  { "results": [
    { "status": "ok", "version": 7, "changeSeq": "1043" },
    { "status": "partial", "version": 3, "rejected": [{ "field": "quantity", "code": "not_finite" }] },
    { "status": "rejected", "code": "parent_deleted" }
  ] }
  ```

  - `status`: `ok` · `partial`(일부 필드만 적용) · `rejected`.
  - 거부 코드: `invalid` · `forbidden` · `deleted` · `parent_deleted` · `parent_missing` · `not_found`.
- 한 요청 최대 200 ops, 본문 1MB.

### 4.3 읽기 `GET /api/sync/pull?cursor=<불투명>&limit=500`

```json
{ "protocol": 2,
  "records": [
    { "type": "holding", "id": "…", "parentId": "…", "version": 4, "changeSeq": "1044",
      "deletedAt": null, "sortKey": "a1", "fields": { …전체 필드… } }
  ],
  "cursor": "<불투명>", "hasMore": false, "reset": false }
```

- `changeSeq` 오름차순. 모든 레코드 타입이 한 흐름에 섞인다. 부모가 먼저 오도록 보장하지는 않는다 → 클라이언트는 한 페이지를 다 받은 뒤 합친다.
- `fields` 는 항상 **전체**다. 클라이언트가 섀도를 새로 만들 수 있게 하기 위해서다.
- 커서 = 사용자별 마지막 `changeSeq` (서버가 base64 로 감싼다). 직렬화 덕분에 겹침 구간이 필요 없다.
- **톰스톤(삭제 기록)은 지우지 않고 계속 보관한다** (사용자 결정). 사용자당 데이터가 작아 쌓여도 부담이 작다.
  - 보관 기간을 두면 허점이 생긴다: 기간보다 오래 꺼져 있던 기기에 이미 지워진 레코드의 수정이 outbox 에 남아 있으면, 서버에 그 레코드가 없으니 `not_found` → `create` 로 되살아난다 ("삭제가 이김" 위반).
  - 톰스톤이 남아 있으면 그 패치는 `deleted` 로 거부되고 기기에서도 지워진다.
  - 정말 커지면 그때 "사용자의 모든 기기가 그 시점 이후 pull 했음"을 확인한 범위만 정리한다 (지금은 만들지 않음).
- `reset: true`: 서버가 데이터를 다시 만들었을 때만 (예: `db:seed:reset`, 복구). 클라이언트는 outbox 를 유지한 채 전체를 다시 받는다.
- 첫 동기화(커서 없음)는 살아 있는 레코드만 준다.

### 4.4 `changeSeq` 구현

- 테이블 `user_sync_state(userId pk, seq bigint not null default 0)`. 일반 테이블이라 `db:generate` 그대로 만든다.
- push 트랜잭션 맨 앞:
  `INSERT … ON CONFLICT (userId) DO UPDATE SET seq = user_sync_state.seq + <ops 수> RETURNING seq`
  → 받은 범위 `seq-n+1 … seq` 를 ops 순서대로 각 레코드 `changeSeq` 에 넣는다.
- 행 잠금이 사용자별 직렬화를 겸한다. advisory lock·전역 시퀀스가 필요 없다.
- 모든 동기화 테이블에 `changeSeq bigint not null`, 인덱스 `(userId, changeSeq)`.
- 서버가 직접 쓰는 경로(`db:seed:reset`, backfill)도 같은 함수로 번호를 받는다. 이 규칙을 어기면 pull 이 변경을 놓치므로 공용 repo 밖에서 동기화 테이블을 쓰지 않는다.

## 5. 클라이언트 동기화 계층

### 5.1 구조

```
UI store (zustand, 중첩 모델 그대로: account.holdings[] …)
   │ 저장 때
   ▼
decompose (정의에서 생성) → 레코드 집합 R_local
   │ diff(섀도 S, R_local) → 바뀐 필드만 패치
   ▼
outbox: Map<type:id, { op, fields(패치 누적), seq }>     ← 기기 저장소(SQLite device_kv)
섀도:   Map<type:id, { version, changeSeq, fields(서버 전체), sortKey }>
   │ push 성공 → 섀도 = 섀도 ⊕ 보낸 패치, version 갱신
   │ pull      → 섀도 = 서버 fields (outbox 에 없는 레코드만 store 에 반영)
   ▼
compose (정의에서 생성) → UI store
```

- 섀도는 diff 의 기준이다. 아는 필드만 비교하므로 모르는 필드는 패치에 절대 들어가지 않는다.
- **기기 레코드 저장소는 서버가 준 레코드를 통째로 보관한다** (모르는 필드·모르는 타입 포함). compose 는 아는 필드만 화면 store 로 올리고, 저장 때는 화면 store 의 아는 필드를 기존 레코드 위에 덮어 쓴다 (`{...기존, ...아는 필드}`). 백업 내보내기는 기기 레코드를 그대로 쓴다.
- 앱 업데이트로 버전이 바뀌면 깨는 변경 `up` 이 있을 때만 기기 데이터·outbox 를 올린다. 확장만이면 할 일이 없다. 어느 경우든 커서는 그대로 써도 된다 (서버 레코드는 언제나 최신 전체 필드).
- **동기화 멈춤 상태** (`426`/`409`): 편집은 계속 기기에 저장된다. 표시는 §5.8.

### 5.2 outbox 규칙

- 같은 레코드의 패치는 합친다 (나중 값이 이김).
- `delete` 가 들어오면 그 레코드의 패치는 버린다. 서버가 모르는 레코드(섀도 없음)면 outbox 에서도 지운다.
- 전송 중에 다시 바뀌면 `seq` 로 구분해 남긴다. 지금의 seq 확인 방식을 유지한다.
- **거부 처리**:
  - `partial`: 적용된 필드는 섀도에 반영한다. 거부된 필드는 기기 **격리 목록**에 `{ type, id, field, value, code, at }` 로 남긴다 (복구·진단용, 사용자에게 목록을 보여 주지 않음). store 값은 서버 값으로 되돌린다.
  - `rejected`: 레코드 패치 전체를 격리 목록으로 옮긴다. `deleted`·`parent_deleted` 는 격리하지 않고 지운다 (다른 기기의 삭제가 이긴 것, 원칙대로).
  - 조용히 덮어쓰지 않는다.
- **재시도**: 제한 시간 15s, 5xx·네트워크 오류 때 지수 backoff (1s → 60s, 지터). `401`·`426` 이면 멈춘다. 앱 복귀(`resume`)·온라인 때 즉시 재시도한다.

### 5.3 저장 앞단 정리

- store 액션이 값을 저장하기 전에 정의의 `normalize` 를 거친다 (NaN → 0, 범위 밖 → clamp).
- `sync-audit.md` 에서 확인한 `parseNumericString("")` = NaN 같은 입력이 저장되지 않는다.
- 정리할 수 없는 값(필수 텍스트가 빈 값 등)은 store 에 남기되 패치에서 그 필드만 뺀다. 기기 격리 목록에 남긴다.

### 5.4 local 모드

- 같은 레코드 저장소(SQLite `records` 테이블, §2.5)를 쓰고 outbox·섀도만 쓰지 않는다.
- **기기 저장은 레코드 단위 upsert** 다. 목록에 없는 행을 지우는 `deleteMissing` 방식을 버린다. 삭제는 "사용자가 지운 레코드 id"로만 한다.
  - 그러려면 저장 어댑터가 store 이전/이후를 비교해 사라진 id 를 계산한다. 지금 `recordLocalChange` 가 하는 계산과 같다.
  - **검증 실패는 기존 행을 그대로 두고, 원본 값을 `device_kv` 격리 키에 남긴다.**
- 브라우저 localStorage 경로는 모바일 웹 종료와 함께 없어진다. 개발용 Vite 브라우저 실행은 **WASM SQLite**(`sql.js` 등)로 같은 `records` 테이블·`CHECK` 제약을 쓴다 (권장, 앱과 동작을 맞추기 위해).

### 5.5 모드 전환

- **local → cloud**:
  1. 서버 전체 pull 로 서버 레코드를 받는다.
  2. 로컬 레코드마다 서버에 없으면 `create`, 있으면 로컬과 다른 필드만 `patch` 로 보낸다 (로컬 우선, 지금 병합 규칙과 같은 결과).
  3. 예외 하나: 포트폴리오의 `growthStage`·`goalAmount`·`goalHistory` 는 묶어서 더 자란 쪽을 고른다 (지금 `keepFurtherPlant` 와 같은 규칙, 이 병합 함수 안에서만).
  - envelope 번역기를 쓰지 않는다.
- **cloud → local**: 전체 pull → 로컬 레코드와 병합(로컬 우선) → 기기 저장. 이후 outbox·섀도는 비운다. 보내지 못한 outbox 가 있으면 전환 전에 마지막 push 를 시도하고, 실패하면 전환을 막는다.
- 전환 중 검증 실패 레코드는 격리한다. 어느 쪽에서도 지우지 않는다 (`sync-audit.md` 손실 경로 3 방지).

### 5.6 백업

- 백업 파일 = `{ format: "seedbook-backup", schemaVersion, exportedAt, records: [...] }`. 정의의 `export` 로 만든다.
- 불러오기:
  - 파일 `schemaVersion` > 앱 → 거부 ("앱을 업데이트한 뒤 불러오세요").
  - ≤ 앱 → 단계 `up` 으로 올림 → `parsePatch(op:create)` → local 이면 기기 저장, cloud 면 push.
  - 옛 백업(2.0 envelope)은 "버전 1" 로 보고, 1 → 2 단계가 envelope 를 레코드로 바꾼다. 별도 변환기를 두지 않는다.
- **데모 데이터 불러오기는 없앤다.** 걷어낼 곳:
  - 설정 "백업·데모 데이터" 화면의 데모 버튼 (`app/m/assets/settings/_components/data-backup-mobile.tsx`, 제목 `app/m/_stack/activities.tsx`).
  - 빈 정원 안내 "설정에서 데모 데이터 불러오기" (`app/m/assets/_components/garden-overview-list.tsx`).

### 5.7 기기 JSON 저장의 무결성

기기 `records.data` 는 JSON 이고, local 모드에서는 유일한 원본이다. 깨지지 않게 하는 장치를 **JS 안의 장치**와 **JS 밖의 장치**로 나눠 둔다. JS 번들 하나의 버그가 모든 기기의 데이터를 한꺼번에 망치지 않게 하기 위해서다.

#### 5.7.1 쓰기 경로 (JS, 한 함수로만)

모든 기기 쓰기는 `writeRecords()` 하나를 거친다. 다른 경로로 `records` 를 쓰지 않는다 (린트로 막음).

1. **정의 검증**: `parsePatch` 로 필드를 검사한다. 실패한 필드는 쓰지 않고 격리한다 (§5.4).
2. **정규 직렬화** `canonicalStringify`:
   - 키 정렬, `undefined` 금지.
   - `NaN`·`Infinity` 는 **예외로 던진다.** `JSON.stringify` 가 조용히 `null` 로 바꾸는 것이 `sync-audit.md` 손실 경로 1 의 원인이었다.
   - 돈(원)은 `Number.isSafeInteger` 를 확인한다.
3. **왕복 확인**: 직렬화한 문자열을 다시 `JSON.parse` 해 원래 값과 깊은 비교. 다르면 쓰지 않고 격리.
4. **체크섬**: 정규 문자열의 SHA-256 (WebCrypto `crypto.subtle`, 의존성 없음)을 `checksum` 열에 함께 쓴다. 손상 감지용이라 보안 목적은 아니다.
5. **이력 보관**: 덮어쓰기 전에 직전 값을 `records_history` 에 남긴다 (레코드당 최근 3개). 한 트랜잭션 안에서 한다.
6. 각 행에 `schemaVersion`, `writtenBy`(앱 번들 버전)를 함께 쓴다. 잘못된 번들이 쓴 행을 나중에 찾아 고칠 수 있게 한다.

#### 5.7.2 읽기 경로

- 읽을 때마다 `JSON.parse` → 체크섬 비교 → 정의 검증.
- 하나라도 실패하면 그 행을 **지우지 않고** 격리 표시하고, `records_history` 의 가장 최근 정상 값으로 화면을 채운다. cloud 모드면 서버에서 그 레코드를 다시 받는다.
- 격리는 진단 로그(값 없이 건수·코드만)에 남는다. 화면 표시는 §5.8.

#### 5.7.3 JS 밖의 장치 (번들 버그에도 남는 것)

| 장치                                                            | 누가 지키나            | 막는 것                                                                                                                                   |
| --------------------------------------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| SQLite 트랜잭션·WAL                                             | SQLite 엔진            | 쓰다 앱이 죽어도 반쯤 쓴 행이 남지 않음                                                                                                   |
| `CHECK (json_valid(data))`, `NOT NULL`, `checksum` 길이 `CHECK` | SQLite 엔진            | 깨진 JSON·빈 값이 아예 저장되지 않음 (JS 가 실수해도 쓰기 실패로 끝남)                                                                    |
| 시작 때 `PRAGMA quick_check`                                    | SQLite 엔진            | 파일 수준 손상 감지 (데이터가 작아 수십 ms)                                                                                               |
| **자동 로컬 스냅샷**                                            | 별도 SQLite 파일       | 하루 1회 + 마이그레이션·OTA 적용 직전에 `records` 전체를 스냅샷 파일로 복사, 최근 7개 보관. 번들 버그로 많은 행이 망가져도 되돌릴 수 있음 |
| 서버 재검증                                                     | 서버 (cloud 모드)      | 기기에서 온 모든 패치를 서버가 같은 정의로 다시 검증. 같은 코드지만 다른 실행 환경                                                        |
| OTA 자동 롤백                                                   | Capawesome live-update | 새 번들이 시작 후 `ready()` 를 부르지 못하면 이전 번들로 되돌림 (`native-deploy.md` A3)                                                   |

- 네이티브(Swift/Kotlin) 플러그인으로 체크섬·스냅샷을 따로 구현하는 방법도 있지만, 두 플랫폼 코드를 더 관리해야 한다. 위 SQLite 제약 + 스냅샷 파일로 "JS 와 독립된 마지막 방어선"은 충분하다고 본다. 운영 중 JS 쪽 사고가 실제로 나면 그때 검토한다.

#### 5.7.4 번들이 바뀔 때 (가장 위험한 순간)

- 기기 저장 틀(`records`·outbox 구조)이나 깨는 변경 `up` 이 필요하면:
  1. 스냅샷 파일을 먼저 만든다.
  2. 새 테이블에 변환해 쓰고, 행 수·체크섬 재계산·정의 검증을 모두 통과하면 그때 교체한다. 기존 테이블은 다음 정상 실행까지 남긴다.
  3. 실패하면 기존 테이블 그대로 실행하고 동기화만 멈춘다.
- OTA 는 단계 배포(일부 기기 → 전체)로 내보낸다. 진단 로그의 체크섬 실패·격리 건수가 늘면 배포를 멈춘다.

#### 5.7.5 테스트

- 직렬화 속성 테스트: 임의 레코드 → `canonicalStringify` → parse → 같음. `NaN`·`Infinity`·`-0`·큰 정수·이모지·서로게이트 문자열 포함.
- 손상 고정 파일: 잘린 JSON, 체크섬 불일치, 모르는 필드, 높은 `schemaVersion` 행 → 지우지 않고 격리, 이력으로 복구.
- SQLite 제약 테스트: JS 검증을 끈 채 깨진 JSON 을 쓰면 SQLite 가 거부한다.
- 실기기 테스트: 같은 테스트를 node SQLite 뿐 아니라 iOS 시뮬레이터·Android 에뮬레이터의 `@capacitor-community/sqlite` 에서 릴리스 전에 한 번 돌린다 (JSON1·WebCrypto 동작 확인).

#### 5.7.6 확인 결과 (2026-11-28, iOS 시뮬레이터·Android 에뮬레이터)

번들 앱과 같은 조건(`server.url` 없이 앱 안 페이지)으로 검사 페이지를 띄워 `@capacitor-community/sqlite` 8.1.1 을 직접 불렀다. 실기기는 연결돼 있지 않아 시뮬레이터로 대신했다. SQLite 라이브러리는 같은 패키지 빌드다.

| 항목                                        | iOS (iPhone 17 시뮬레이터)           | Android 17 (에뮬레이터, WebView Chrome 145) |
| ------------------------------------------- | ------------------------------------ | ------------------------------------------- |
| origin / `isSecureContext`                  | `capacitor://localhost` / true       | `https://localhost` / true                  |
| `crypto.subtle.digest("SHA-256")`           | 동작, 값 일치                        | 동작, 값 일치                               |
| SQLite / SQLCipher                          | 3.54.1 / 4.20.0 community            | 3.53.3 / 4.17.0 community                   |
| `json_valid` · `json_extract`               | 동작                                 | 동작                                        |
| `CHECK (json_valid(data))` 깨진 JSON insert | **거부** (`CHECK constraint failed`) | **거부**                                    |
| `CHECK (length(checksum) = 64)`             | 거부                                 | 거부                                        |
| `PRAGMA quick_check`                        | ok                                   | ok                                          |

- 두 플랫폼의 SQLite 버전이 다르다 (플러그인이 플랫폼별 SQLCipher 를 따로 묶음). JSON 함수는 3.38 부터 기본 포함이라 둘 다 문제없지만, 버전 차이에 기대는 SQL 은 쓰지 않는다.
- 지금 원격 셸(`https://seedbook.boogie.ing`)도 보안 컨텍스트라 `crypto.subtle` 이 된다.

### 5.8 동기화 상태 표시 (사용자 결정)

- **건수·목록은 보여 주지 않는다.** 보내지 못한 변경 수, 격리 목록 화면을 두지 않는다. 사용자가 할 수 있는 일이 없는 정보라서다.
- **홈에는 문제가 오래 갈 때만 표시한다** (cloud 모드):

| 조건                                                        | 언제   | 문구 예                             | 누르면                    |
| ----------------------------------------------------------- | ------ | ----------------------------------- | ------------------------- |
| 마지막 동기화 성공이 **3일**(권장 기본값) 넘게 지남         | 3일 뒤 | "며칠째 동기화되지 않았어요"        | 설정 > 데이터 > 저장 위치 |
| 앱 업데이트 필요 (`426`)                                    | 바로   | "업데이트하면 동기화가 다시 켜져요" | 스토어                    |
| 격리 발생 (거부·검증 실패, 원래 일어나면 안 되는 버그 상태) | 바로   | "일부 변경을 저장하지 못했어요"     | 저장 위치                 |

- `409`(앱이 서버보다 새것)·네트워크 오류·5xx 는 3일 조건으로만 드러난다. 잠깐의 실패로는 아무것도 표시하지 않는다.
- **설정 > 데이터 > 저장 위치** (기존 화면) 의 클라우드 항목 아래에 "마지막 동기화: ○월 ○일 ○시" 와 멈춘 이유 한 줄만 보인다. 새 메뉴는 만들지 않는다.
- 상태는 기존 `features/settings/stores/sync-status-store.ts` 에 `lastSuccessAt`·`stoppedReason`·`hasQuarantine` 으로 둔다.

## 6. 서버 구조

```
app/api/sync/push/route.ts   → server/sync/push.ts     (인증·헤더·직렬화 락·ops 루프)
app/api/sync/pull/route.ts   → server/sync/pull.ts     (changeSeq 커서·페이지·reset)
server/sync/record-repo.ts   → 정의 하나로 동작하는 공용 repo (create/patch/delete/changes)
packages/domain/records/*.ts → 레코드 정의
```

- 도메인별 `*-sync.ts`·`*-record.ts`·`_translators/*` 는 정의 + 공용 repo 로 대체한다.
- 도메인 고유 규칙은 정의의 훅으로만 둔다: `onParentDelete`, 파생 작업 `afterCommit`.
  - 파생 작업의 예: cloud 사용자의 일별 기록은 crawler 가 쓰므로 훅이 필요 없다.
- **관측**:
  - 요청마다 `{ userId 해시, protocol, client, ops 수, partial/rejected 수, 코드별 수, 처리 ms }` 를 구조화 로그로 남긴다.
  - 거부가 생기면 `{ type, field, code }` 를 남긴다. 값은 남기지 않는다 (개인정보).
- **백업**: 동기화 테이블은 Supabase 일일 백업·PITR 설정을 확인하고 문서화한다 (미확인 항목).
  - contract 마이그레이션 직전에는 해당 테이블을 덤프한다 (운영 절차).

## 7. 데이터 버전 모델 (핵심)

### 7.1 규칙 (사용자 결정)

1. **서버 스키마는 확장만 한다.** 새 버전은 옛 버전을 그대로 품는다 (옛 필드·옛 의미·옛 값 범위를 바꾸지 않고 더하기만).
2. 그래서 **옛 앱도 서버와 동기화한다.** 막는 것은 두 경우뿐이다.
   - 앱이 `MIN_SCHEMA` 보다 낮다 → `426`. `MIN_SCHEMA` 는 확장으로 표현할 수 없는 변경(§7.4 "깨는 변경")을 했을 때만 올린다.
   - 앱이 서버보다 높다(앱이 서버 배포보다 먼저 깔림) → `409 schema_ahead`, 앱은 조용히 기다린다.
   - 막힌 동안에도 편집은 기기에 저장되고 outbox 에 쌓인다.
3. **백업(JSON) 불러오기는 파일 버전 ≤ 앱 버전일 때만.** 낮으면 `up` 으로 올려서 넣는다.
4. **데모(테스트) 데이터 불러오기는 없앤다** (§5.6).
5. 이 방식은 **규칙을 철저히 지켜야** 성립한다. 규칙은 사람의 리뷰가 아니라 CI 가 막는다 (§7.5).

### 7.2 옛 앱이 새 데이터를 망치지 않는 이유

세 가지가 함께 있어야 한다. 하나라도 빠지면 확장 규칙이 무너진다.

| 장치                                 | 막는 것                                                                                                                                                               |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **패치 의미** (원칙 2)               | 옛 앱은 자기가 고친 필드만 보낸다 → 모르는 새 필드를 덮지 않는다                                                                                                      |
| **`default` 는 생성 때만**           | 옛 앱의 패치에 서버가 새 필드 기본값을 채워 넣지 않는다                                                                                                               |
| **기기는 받은 레코드를 통째로 보관** | 옛 앱의 기기 저장·백업 내보내기·모드 전환에서 새 필드가 빠지지 않는다. 화면 store 는 아는 필드만 쓰지만, 기기 `records.data` 에 서버가 준 레코드 전체가 남는다 (§2.5) |

### 7.3 변환은 기기 안 올림(`up`)만

- 확장 변경은 **변환이 필요 없다.** 서버에도 기기에도 변환 코드가 없다. 옛 앱은 모르는 필드·모르는 레코드 타입을 그대로 둔다.
- 깨는 변경(드묾)만 변경 단계 `up` 을 적는다. 같은 함수를 세 곳이 쓴다: 기기의 앱 업데이트 마이그레이션, 백업 불러오기, 서버 backfill.
- 내림(`down`)은 없다. 깨는 변경 전 버전의 앱은 `MIN_SCHEMA` 로 막히기 때문이다.
- 단계는 지우지 않는다 (오래된 기기·옛 백업이 여러 버전을 건너뛴다).

### 7.4 변경 분류: 확장 vs 깨는 변경

| 변경                                                                | 분류                                                                                                                     | 지킬 조건                                                                                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 필드 추가                                                           | 확장                                                                                                                     | 생성 때 `default` 또는 nullable. 옛 앱이 만든 레코드도 유효해야 함                                                           |
| 레코드 타입 추가                                                    | 확장                                                                                                                     | 옛 앱은 모르는 타입을 보관만 하고 그리지 않는다. 옛 앱이 부모를 지우면 서버가 하위 톰스톤을 찍으니 안전                      |
| enum 값 추가                                                        | 확장 **(그 필드가 `open: true` 일 때만)**                                                                                | 옛 앱이 모르는 값을 받으면 "기타"로 보이고, 사용자가 바꾸기 전에는 보내지 않는다. `open` 이 아닌 enum 에 값 추가는 깨는 변경 |
| 검증 완화 (`max` 늘림 등)                                           | 확장                                                                                                                     | —                                                                                                                            |
| 새 필드가 옛 필드와 함께 맞아야 함 (예: `goalAmount`·`goalHistory`) | 확장 **(서버 훅으로만)**                                                                                                 | 옛 앱이 한쪽만 바꿔도 서버 `afterWrite` 훅이 다른 쪽을 맞춘다. 훅으로 못 맞추면 깨는 변경                                    |
| 필드 이름 변경                                                      | **금지** → 새 필드 추가 + 옛 필드 `deprecated` (계속 읽고 씀, 서버 훅이 둘을 맞춤). 옛 필드를 실제로 없애는 건 깨는 변경 |                                                                                                                              |
| 단위·의미·타입 변경                                                 | **금지** → 새 필드로                                                                                                     |                                                                                                                              |
| 필드 제거                                                           | 깨는 변경                                                                                                                |                                                                                                                              |
| 검증 강화                                                           | 깨는 변경 (옛 앱이 만들 수 있는 값을 거부하게 되므로). 기존 값을 `normalize` 로 고칠 수 있으면 확장                      |                                                                                                                              |
| 레코드 쪼개기·합치기                                                | 깨는 변경                                                                                                                |                                                                                                                              |

- 깨는 변경은 묶어서 드물게 한다. 절차는 §8 의 B.

### 7.5 규칙을 지키게 하는 장치 (CI)

1. **스키마 스냅샷**: 출시한 버전마다 정의를 JSON 으로 `packages/domain/schema-snapshots/v<N>.json` 에 커밋한다 (스크립트가 만듦, 지우지 않음).
2. **호환 검사** (`pnpm schema:check`, CI 필수): 현재 정의를 직전 스냅샷과 비교해 위 표대로 분류한다.
   - 정의가 바뀌었는데 `schemaVersion` 을 안 올렸으면 실패.
   - 깨는 변경이 있는데 `MIN_SCHEMA` 를 같은 PR 에서 올리지 않았으면 실패.
   - 확장 조건 위반(기본값 없는 필수 필드, `open` 아닌 enum 에 값 추가, `min` 올림 등)은 실패.
3. **옛 앱 재생**: 지원 구간 `[MIN_SCHEMA, CURRENT]` 의 모든 스냅샷 N 에 대해
   - N 의 정의로 만든 임의 패치를 최신 서버에 보낸 뒤, N 이 모르는 필드가 그대로인지.
   - 최신 서버 레코드를 N 의 정의로 읽어도 실패하지 않는지 (모르는 필드·enum 값 포함).
   - N 의 기기가 받은 레코드를 저장 → 내보내기 → 다시 불러오기 해도 새 필드가 남는지.
4. 스냅샷·재생 고정 파일은 리뷰에서 "지우지 않았는지"만 보면 된다. 판단은 기계가 한다.

### 7.6 버전 정리

| 버전                             | 뜻                           | 언제 올리나                                  |
| -------------------------------- | ---------------------------- | -------------------------------------------- |
| **`schemaVersion`**              | 데이터 모양                  | 정의가 바뀔 때마다 (확장 포함)               |
| **`MIN_SCHEMA`**                 | 서버가 받는 가장 옛 버전     | 깨는 변경 때만                               |
| **프로토콜** (`x-seedbook-sync`) | push/pull 전송 형식          | 거의 안 바뀜. 바뀌면 깨는 변경과 같게 다룸   |
| **DB 마이그레이션**              | 서버 컬럼 (기기는 저장 틀만) | 필드 추가 때 `db:generate`. 확장 규칙을 따름 |

- 앱 최소 버전은 `MIN_SCHEMA` 로 대신한다. 동기화와 무관한 강제 업데이트가 필요할 때만 `/api/app-config` 를 쓴다.
- store persist version 과 envelope VERSION 은 없어진다.

## 8. 스키마 변경 플레이북

**A. 확장 (대부분)** — 옛 앱을 막지 않는다.

1. 정의 수정 + `schemaVersion` +1. 스냅샷 갱신. `schema:check` 통과.
2. `db:generate` 로 nullable/default 컬럼 추가 (기기는 할 일 없음).
3. **서버 먼저 배포.** 옛 앱은 계속 동기화하고 새 필드는 건드리지 않는다.
4. 앱은 아무 때나 출시. 서버보다 먼저 깔리는 경우만 `409` 로 잠깐 기다린다.

**B. 깨는 변경 (드묾, 묶어서)** — 옛 앱의 동기화를 멈춘다.

1. 정의 수정 + `schemaVersion` +1 + `MIN_SCHEMA` = 새 버전 + `up` 단계.
2. 서버 backfill 은 같은 `up` 함수.
3. 앱 빌드 → 심사 통과 → 스토어 "수동 출시"로 대기.
4. 서버 배포 + backfill. 이때부터 옛 앱은 `426` (기기 저장은 계속).
5. 바로 앱 공개 (OTA 면 번들 배포). 업데이트한 기기는 기기 데이터·outbox 를 `up` 하고 동기화를 다시 시작한다.

- 이름 변경·의미 변경이 필요하면 먼저 A 로 새 필드를 추가해 쓰고, 옛 필드 정리는 다음 B 에 모아서 한다.

**PR 체크리스트** (CLAUDE.md 에 넣음):

1. 정의를 바꿨는가? 손으로 쓴 사본이 남지 않았는가?
2. `schema:check` 가 이 변경을 확장으로 분류하는가? 깨는 변경이면 `MIN_SCHEMA`·`up`·backfill 이 같은 PR 에 있는가?
3. 대조 테스트(정의 ↔ drizzle ↔ 기기)와 옛 앱 재생(§7.5-3)이 통과하는가?
4. 스냅샷·고정 파일을 지우지 않았는가?
5. 릴리스 순서(A: 서버 먼저 / B: 심사 통과 → 서버 → 앱 공개)를 PR 본문에 적었는가?

## 9. 테스트 아키텍처

1. **정의 대조 테스트** (단위): 정의 ↔ `schema.ts` 컬럼·타입·nullable·default, 정의 ↔ 기기 `records` 왕복(저장 → 읽기에서 모르는 필드 포함 그대로).
2. **호환 검사 + 옛 앱 재생**: §7.5 의 `schema:check` 와 재생 테스트. 추가로
   - 깨는 변경 `up`: 모든 N 의 기기 DB·outbox·백업 고정 파일(`fixtures/schema-v<N>/`)을 올리면 정의 검증을 통과하고 레코드 수가 줄지 않는다. 서버 backfill 과 같은 결과.
   - 버전 게이트: `MIN_SCHEMA` 미만 `426`, 서버보다 높으면 `409`, 높은 버전 백업은 거부.
3. **패치 속성 테스트** (단위): 임의 레코드·임의 편집 순서에서 다음을 확인한다.
   - "안 보낸 필드는 바뀌지 않는다"
   - "삭제 뒤 패치는 거부된다"
4. **오래된 기기 시나리오** (통합, 하나):
   - 실제 push/pull 핸들러 + 테스트 DB.
   - 기기 B(새 버전)가 새 필드를 쓰고 일부를 지운다 → 옛 버전 기기 A 가 오래 오프라인이다 돌아와 같은 레코드를 편집·push·pull, 백업 내보내기, local 전환 → B 의 새 필드·삭제와 A 의 편집이 모두 남는지 본다. `reset` 도 이 시나리오 위에서 돈다.
5. **기기 무손실** (단위): 검증 실패·NaN·범위 밖 값을 저장해도 기존 행이 남고 격리 키에 원본이 생기는지 본다. `sync-audit.md` 재현 테스트가 RED 로 출발점이 된다.
6. **커서 정확성** (DB 통합): push 여러 번 + 페이지 나눠 pull 에서 빠지거나 중복되는 레코드가 없는지 본다.

## 12. 남은 결정 (권장 기본값으로 설계함)

0. 사용자 데이터 저장 구조: **서버 = 필드별 컬럼, 기기 = 레코드 JSON** (사용자 결정, §2.5).
1. 톰스톤 보존: **계속 보관** (사용자 결정, §4.3).
2. 동기화 상태 표시: **건수·목록 없음, 홈에는 3일 넘게 동기화 실패·업데이트 필요·격리 때만, 저장 위치 화면에 마지막 동기화 시각** (사용자 결정, §5.8). 3일은 권장 기본값.
3. 삭제가 이김 (되살리기 없음): **권장**. 실수 복구는 클라이언트 실행 취소로.
4. 개발용 브라우저 실행의 저장소: **WASM SQLite 권장** (§5.7 의 SQLite 제약을 브라우저에서도 그대로 검증). 개발 흐름은 `native-deploy.md` §A1 "개발 흐름".
